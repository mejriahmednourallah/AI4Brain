# AI4BRAIN: An Evidence-Grounded Cognitive Growth Demonstrator

**Technical report | Software implementation and verification record | 22 October 2026**

## Abstract

AI4BRAIN is a local, non-clinical software demonstrator for brief cognitive-task practice. Its five task families, server-owned scoring, evidence-aware selection, adaptive practice, versioned plans, constrained text coach and two dashboard presentations form a software loop: a saved response can be traced to a task-specific estimate and a reproducible next decision. Missing, interrupted and assisted evidence stay distinct from valid unassisted baseline evidence.

React, TypeScript and Vite provide the interface; FastAPI owns task evaluation and policy; SQLite is the canonical event store; Neo4j is an optional derived graph. Remote coach generation is opt-in and was not used in the recorded checks. Brief self-authored task sets are not validated psychometric instruments. Indices are preliminary within-task observations with high uncertainty, not IQ, diagnoses, percentiles or comparable measurements across families.

The verification record includes isolated API and policy smokes, recorded browser QA and a read-only Neo4j inspection. Dashboard aggregation has a disposable-database smoke. The connected-agent loop (evidence â†’ explanation â†’ learner-chosen action â†’ practice â†’ outcome â†’ updated plan and Twin) is implemented and its contracts are covered by dedicated suites: 40 named coaching/evaluation cases and a 68-case recovery matrix across all eleven activities pass on disposable data. Browser QA attempts are software test data, not participant results. Human acceptance, clinical validation, live provider behaviour and submission are not established.

## 1. Scope and source basis

The product follows the supplied AI4BRAIN POC specification and the current Sprint 01-04 execution plan. Those documents specify the five families, evidence-linked profile, explainable selector, adaptive practice, collaboration rubric, coach boundaries, Analytics and RPG modes, and local data controls. Their competition dates and submission rules remain claims in supplied materials and have not been independently verified.

The product intentionally reports task performance rather than cognitive traits. It makes no claim about school or work transfer, general intelligence, or comparative ability. Browser timing is approximate and device-dependent. Synthetic examples are isolated and labeled; automated QA history in the development database is not sample participant data.

## 2. Architecture and evidence flow

The user journey starts with a non-clinical notice and consent, then practice, five task baselines, an evidence overview and optional training. Users can inspect the Brain Twin graph and switch between Analytics and RPG presentation. Both modes use the same task profile; XP and levels represent engagement only. The companion is quiet during scored baseline and reassessment. Training assistance is recorded as assisted evidence.

The browser submits a response, not a score. FastAPI validates the phase, item version, ownership and response shape, then evaluates against server-owned task definitions. SQLite stores immutable events with phase, item configuration, response, evaluation, timing, hint/interruption flags and evidence IDs. Snapshots, recommendations and plans derive from canonical events. Exact event-ID retries replay the saved result; changed retries conflict. Interrupted work remains auditable but cannot fill scored evidence slots. Baseline, practice, training and reassessment use separate identities.

Each task estimate uses a coherent baseline session. Missing slots are not borrowed from earlier sessions or practice. Reassessment uses a separate comparable item set and does not overwrite the initial baseline. Fixed item uniqueness and transactional replay guards protect the event history. Client timing is labeled approximate. Planning efficiency is recomputed against a server-verified shortest path.

Selection and planning are deterministic backend modules. Recommendations preserve action, tier, reasons, observed features, alternatives, policy version and supporting IDs. Plans contain two to four steps, budget, estimated minutes, goal, reasons and evidence references. A material change creates new plan history; unchanged inputs remain unchanged. Neo4j is an optional mirror, not a source for scores or attempts. A prior live adapter check verified a repeatable SQLite-derived sync; the newer read-only check inspected graph references. Neither establishes production readiness.

## 3. Task families and interpretation

| Family | Baseline sample | Task-specific display index |
|---|---:|---|
| Spatial sequence recall (EX-01) | 6 sequences: 2 each at lengths 3, 4 and 5 | 100 x correctly recalled positions / 24; longest fully correct span is separate. |
| Pattern reasoning (EX-02) | 6 original 2x2 patterns | 100 x correct items / 6; evaluation is server-side. |
| Go/no-go attention (EX-03) | 40 trials: 30 Go, 10 No-go | 50 x (Go hit rate + No-go correct-rejection rate); component counts remain visible. |
| Rule switching (EX-04) | 24 trials: 8 switches, 16 repeats | 50 x (switch accuracy + repeat accuracy); rates remain inspectable. |
| Minimum-move planning (EX-05) | 3 solvable puzzles | Mean of puzzle efficiencies; each completed puzzle is min(100, 100 x BFS shortest path / legal moves). Incomplete puzzles contribute zero. |

The indices are not cross-family normalized. An 80 in one family does not imply stronger ability than a 70 in another. A completed brief profile remains high-uncertainty; incomplete evidence stays incomplete or unassessed rather than being represented as a fabricated zero. Three planning puzzles are sparse evidence. Reassessment sets are designed to be comparable but have not been empirically equated.

## 4. Personalization, coach and collaboration

The `personalization-v1` selector checks family-specific evidence before recommending targeted training. Missing evidence routes to assessment. The four normalized features are performance gap (0.40), explicit goal (0.25), recency (0.20) and uncertainty need (0.15). Every fourth eligible selection explores the least-recently practiced family. This is a documented heuristic, not a trained or validated model. Synthetic-only scenarios demonstrate differing decisions without inserting learner events.

Four distinct, uninterrupted, same-family and same-tier training attempts drive a versioned up/down/hold rule using family-specific success definitions. Three or more successes promote, one or fewer demote, and two hold. A hint in the window prevents treating that evidence as unassisted; interrupted attempts remain retryable. Strategies are linked to recorded error categories and source events. Training never changes the fixed baseline score.

The local coach fallback describes supported evidence, an allowed next task or tier, a permitted strategy and uncertainty. Remote use is opt-in, requires recorded consent on every request, and reports the requested provider, the provider actually used, the model, a fallback reason and a status â€” including a distinct `timeout` status. Structured output is constrained to approved choices and evidence IDs; a validation layer rejects any provider prose that restates a measured value — including digits, spelled-out numbers and noun-plus-value clauses — so every factual clause is server-authored; it also rejects a wrong family or tier, invented evidence or strategy identifiers, unrecorded assistance claims, certainty the uncertainty status does not support, and clinical assertions about the learner. The route rejects scored baseline and reassessment requests, and training assistance is tied to an active block/item. No live provider call is claimed.

The connected-agent contract versions the coach as `coach-v2`, the plan as `plan-v2` and collaboration as `collaboration-v2`, while earlier records stay readable. A derived Twin context separates `observed`, `learner_reported` and `suggested` facts and carries an evidence revision; only observed facts may carry measured values. One resolver outcome governs the recommendation, the plan's first step and the launch; an explicit availability constraint is honoured rather than silently ignored, and when the budget cannot fund the resolved activity the plan says so and offers the budget change. Subject resolution prefers an explicitly named family, then the current activity, then the established conversation subject, and only for "what next" questions the next recommendation; genuine ambiguity asks one short clarification. Coaching requests reserve a request ID with a canonical payload hash before generation, so an exact retry replays, a conflicting payload is refused, a duplicate in flight is refused, and an abandoned reservation is reclaimable. Follow-up questions receive a bounded, ordered learner-plus-assistant history with provenance. Approved actions are re-validated against the saved turn before anything is recorded or opened, so the learner chooses the action rather than the coach acting. The optional companion voice is local KittenTTS synthesis of validated reply text, off by default, with one audio owner, explicit stop, and complete silence while a timed or scored activity is active.

The proposed collaboration rubric covers clarification (20%), critical verification (25%), iteration (20%), autonomy (20%) and responsible use (15%). Genuine opportunities and actions link to canonical events. A verification claim's expected verdict is derived per saved record rather than fixed, the safe adjudicating fields (task family, phase, scored status, saved response, server evaluation, assistance and interruption state, source record) are shown before the learner answers, and answers stay server-side. Each dimension remains unassessed until evidence exists. This is a proposed POC interaction rubric, not a validated measure of intelligence, trust or general AI literacy.

Recorded verification includes disposable-DB smokes for core events and replay, five task banks/scorers, personalization and plan history, coach boundary/fallback, collaboration events, lifecycle operations, graph derivation, and dashboard aggregation. The dashboard smoke checks missing nullable values, event filtering for engagement, invariance across dashboard modes, and read-only behavior. The project virtual environment compiles the backend; Vite production-build and real-browser review are separate acceptance layers.

The correction pass of 22 October 2026 added contract-level evidence for the connected agent. `r1_rj01_rj02_smoke.py` proves atomic request reservation with exact replay, conflicting-payload rejection, in-progress and concurrent 200/409 behaviour, one canonical event per accepted request, learner-scoped export/deletion that now includes coaching turns, conversations and collaboration claims, and refusal of a reply whose learner data was deleted mid-flight. `r2_rj03_rj04_rj06_smoke.py` proves field-bound factual validation, canonical family/tier/strategy/evidence whitelists, refusal of unsupported certainty and clinical assertions, a distinguishable provider-timeout status, an ordered learner-plus-assistant history carrying provenance, and plan/launch tier agreement under promote, hold and demote. `r4_case_manifest.py` executes forty named cases across family explanations, missing/partial/ambiguous evidence, eight adversarial outputs, history/action/plan, retry/concurrency/restart, provider states and quiet/speech/lifecycle, recording input, expectation, observation, verdict and source for each; all forty pass. `r5_recovery_matrix.py` covers a rejected save, a lost reply, a conflicting payload, a failed GET, a reload restore and an interrupted completion for the five families and six hybrid activities; all sixty-eight pass. `output/verification/r6-reproduction/REPORT.md` reruns each reproduced finding from the 22 October rejudgment against the current tree, and `scripts/r7_rejudge_fixes_smoke.py` closes the four problems that rejudgment then raised (including restated-fact paraphrases, an empty availability list that meant "everything", and a recommendation that disagreed with the scheduled plan).
